## 7. Process and Thread State Inspection

### Process Tree Anomaly Detection

The process tree is a fundamental structure in operating systems that represents the hierarchical relationships between processes. Each process has a parent process, and together they form a tree-like structure where the root process (typically `init` or `systemd` on Linux) serves as the top-level node. This hierarchical organization allows for efficient resource management, process scheduling, and inter-process communication. However, the integrity of this structure can be compromised by malicious activities such as root access, jailbreaking, emulator usage, hooking, or tampering. These anomalies often manifest as deviations from expected parent-child relationships, unexpected process spawning patterns, or the presence of foreign processes in the tree. Detecting such anomalies is a critical component of runtime-integrity detection systems and forms the foundation for identifying potentially compromised environments.

At the core of process tree anomaly detection lies the inspection of process parentage and lineage. A normal process tree should exhibit predictable patterns, with each child process having a clear and consistent parent. For example, in a typical Android system, the `zygote` process spawns all application processes, and each of these processes has a direct parent-child relationship with `zygote`. Deviations from this structure—such as a process having an unexpected parent or a process spawning multiple children without a clear lineage—can indicate tampering. One concrete example is the presence of a "root" process that spawns multiple child processes outside of the expected hierarchy. This could be a sign of a root exploit or a malicious emulator attempting to simulate a rooted environment.

To detect such anomalies, runtime-integrity detection systems can analyze the process tree by traversing from the root process downward and verifying the consistency of parent-child relationships. A key mechanism involves comparing the actual parent process ID (PID) of each child process with the expected parent PID based on the system's normal behavior. For instance, in a typical Android environment, the `zygote` process (PID 1) should be the immediate parent of all application processes. If a process is found to have a different parent, such as a non-existent or foreign PID, this can signal an anomaly. Additionally, the system can track the number of children each process spawns and compare it against historical or baseline data. A sudden increase in child processes, especially from a non-standard parent, may indicate a hook or tamper event.

Another important aspect of process tree anomaly detection is the identification of unexpected process spawning patterns. In a normal environment, processes are spawned in a predictable manner based on the application's lifecycle and system events. However, malicious activities can introduce irregularities. For example, a root exploit might spawn multiple child processes with inconsistent parentage, creating a "branch" in the tree where none should exist. Similarly, an emulator could simulate a rooted environment by introducing processes that do not align with the expected hierarchy. These anomalies can be detected by analyzing the process tree for unexpected branches, orphaned processes, or processes that do not follow the expected spawning order.

One concrete example of this is the detection of "stray" processes in the tree. A stray process is one that has no clear parent or is spawned without following the normal process lifecycle. These can be identified by checking for processes whose parent PID does not exist or corresponds to a non-standard process. For instance, in a typical Android system, the `zygote` process should have a direct relationship with all application processes. If a process is found to have a parent PID that does not correspond to a known system process, such as `init` or `zygote`, this could indicate an anomaly. This method can be further refined by comparing the process tree against historical data or known patterns for the specific operating system and environment.

The detection of unexpected process spawning patterns also involves analyzing the timing and frequency of process creation. In a normal environment, processes are spawned in response to specific events, such as application launches or system updates. However, malicious activities can introduce irregularities in this pattern. For example, a root exploit might spawn multiple child processes simultaneously without any clear trigger, leading to an unusual spike in the number of active processes. This can be detected by analyzing the process tree for sudden increases in the number of child processes or by identifying processes that are spawned at inconsistent intervals.

Another key aspect of process tree anomaly detection is the identification of foreign processes in the tree. A foreign process is one that does not belong to the expected hierarchy and may have been introduced through tampering or hooking. These processes can be identified by comparing the process tree against a known baseline or by analyzing the parent-child relationships for inconsistencies. For example, if a process with an unexpected parent PID is detected, this could indicate the presence of a foreign process. This method is particularly effective in environments where the process tree is expected to follow a strict hierarchy, such as in Android or iOS systems.

To further enhance the detection of anomalies, runtime-integrity detection systems can leverage tools and mechanisms that provide detailed insights into the process tree. For instance, the `ps` command on Unix-like systems allows for the inspection of process information, including parent PIDs and process hierarchies. Similarly, the `proc` filesystem in Linux provides access to detailed process data, enabling the analysis of process relationships. These tools can be used to traverse the process tree and identify any deviations from the expected structure. For example, by iterating through all processes and comparing their parent PIDs against a known baseline, an anomaly can be detected if a process has an unexpected parent or if a process is found without a clear lineage.

In addition to these mechanisms, runtime-integrity detection systems can also incorporate machine learning techniques to detect anomalies in the process tree. By analyzing historical data on process spawning patterns and parent-child relationships, these systems can identify deviations that may indicate tampering or hooking. For example, a machine learning model trained on normal process tree structures can flag any deviations from the expected patterns as potential anomalies. This approach is particularly effective in detecting subtle anomalies that may not be easily identifiable through traditional methods.

Overall, the detection of process tree anomalies involves a combination of techniques, including the inspection of parent-child relationships, the identification of unexpected spawning patterns, and the detection of foreign processes. These methods can be applied to various operating systems and environments, enabling the identification of potential compromises such as root access, jailbreaking, or emulator usage. By leveraging concrete mechanisms and tools, runtime-integrity detection systems can effectively monitor the process tree for anomalies and provide a foundation for more advanced runtime-integrity analysis.

### Thread Priority and Scheduling Analysis

The thread priority and scheduling analysis is a critical component of process and thread state inspection, particularly within the context of runtime-integrity detection systems such as rootsentry. This analysis leverages low-level scheduling information to detect anomalies in thread behavior that may indicate root/jailbreak/emulator/hook/tamper activities. By examining the scheduling priorities and quantum allocations of threads, we can identify deviations from expected behavior, which often correlate with malicious or non-standard runtime environments.

At the core of this analysis is the operating system's scheduling mechanism, which assigns a priority to each thread and determines the order in which threads are executed. In Linux, for example, thread priorities are managed through the `nice` value and the real-time scheduling policies such as `SCHED_FIFO` and `SCHED_RR`. The `nice` value ranges from -20 (highest priority) to 19 (lowest priority), while real-time threads have fixed priorities ranging from 1 to 99. These values are stored in the thread's task structure (`struct task_struct`) and can be accessed via `/proc/<pid>/task/<tid>/sched` or through system calls such as `sched_getparam()`. By inspecting these values, we can determine whether a thread is operating under normal conditions or if it has been manipulated to gain an unfair advantage in the scheduling hierarchy.

One of the most common anomalies detected through thread priority analysis is the presence of threads with abnormally high priorities. For instance, in a rooted environment, an attacker may elevate the priority of a malicious thread to ensure it executes before legitimate threads, thereby increasing its chances of success. This can be observed by checking for threads with `nice` values less than -10, which are typically reserved for system-level processes. Similarly, real-time scheduling policies may be misused to bypass normal scheduling constraints, leading to priority inversion or starvation of other threads. Such anomalies can be flagged as potential indicators of root or jailbreak activity.

In addition to thread priorities, the scheduling quantum—the amount of CPU time allocated to a thread before it is preempted—is another important metric for analysis. In Linux, the quantum for normal (CFS) scheduling is typically 100 microseconds, but it can be adjusted based on system load and configuration. Threads with artificially inflated or reduced quantum values may indicate tampering with the scheduling mechanism. For example, a thread with an excessively long quantum could be designed to monopolize CPU resources, while a thread with an unusually short quantum might be attempting to minimize its execution time to avoid detection.

The scheduling policy itself can also serve as a valuable indicator. While most threads operate under the default CFS (Completely Fair Scheduler) policy, certain environments—such as emulators or hooking frameworks—may employ alternative policies to simulate different runtime conditions. For instance, an emulator might use `SCHED_FIFO` to prioritize its internal emulation threads, thereby altering the normal scheduling behavior of the host system. Similarly, hooking frameworks may inject threads with real-time policies to ensure that their hooks are executed before the main application threads, allowing for more effective interception and modification of function calls.

To perform a thorough analysis of thread priority and scheduling, we can use a combination of static and dynamic inspection techniques. Static inspection involves examining the `/proc/<pid>/task/<tid>/sched` file, which contains detailed information about each thread's scheduling parameters. This file includes the current scheduling policy, priority, and quantum values, as well as historical data such as the last time the thread was scheduled. Dynamic inspection, on the other hand, involves using system calls such as `sched_getparam()` and `sched_setscheduler()` to retrieve and modify scheduling parameters in real-time. These techniques allow us to monitor thread behavior continuously and detect any deviations from expected patterns.

One of the key challenges in thread priority analysis is distinguishing between legitimate high-priority threads and malicious ones. For example, system daemons such as `kthreadd` or `systemd` often operate with elevated priorities to ensure they are executed promptly. However, in a rooted environment, an attacker may inject a malicious thread with a similar priority to gain control over critical system functions. To mitigate this, we can analyze the context in which a high-priority thread is created. For instance, threads spawned by root processes or those with unusual parentage (such as threads originating from `/system/bin` or `/data/local`) may be flagged for further inspection.

Another important consideration is the interaction between multiple threads and the overall system load. In normal operation, threads are scheduled based on their priority and fairness, but in a tampered environment, this balance can be disrupted. For example, an emulator might create a large number of threads with elevated priorities to simulate a multi-core device, thereby masking its true nature. This can be detected by analyzing the distribution of thread priorities across the process and comparing it to expected patterns. A sudden increase in the number of high-priority threads or an unusual clustering of priorities may indicate an emulator or hooking framework in use.

In addition to priority and scheduling policies, we can also analyze the behavior of threads during execution. For instance, a thread with an unusually long execution time may be attempting to perform extensive computations under the radar, while a thread that frequently preempted may be trying to avoid detection by minimizing its runtime. These behaviors can be further validated by examining the thread's CPU usage and I/O activity, which can be retrieved from `/proc/<pid>/task/<tid>/stat` or through system calls such as `getrusage()`.

To implement this analysis in a practical setting, we can use a combination of tools and techniques. For example, the `ps` command can provide a high-level overview of thread priorities and scheduling policies, while more advanced tools like `perf` or `ftrace` can offer detailed insights into thread behavior. Additionally, custom scripts can be written to parse `/proc/<pid>/task/<tid>/sched` and compare the observed values against known baseline patterns. These scripts can also monitor changes in thread parameters over time, detecting any sudden modifications that may indicate tampering.

In summary, the analysis of thread priority and scheduling is a powerful technique for detecting runtime-integrity violations. By examining the scheduling policies, priorities, and quantum allocations of threads, we can identify anomalies that may indicate root/jailbreak/emulator/hook/tamper activities. This analysis is particularly effective when combined with other inspection techniques, as it provides a comprehensive view of thread behavior and its impact on system integrity. Through careful examination of scheduling parameters and their context, we can uncover subtle signs of tampering that might otherwise go unnoticed, thereby enhancing the overall effectiveness of runtime-integrity detection systems.

### Memory Mapping and Shared Library Verification

The integrity of memory mapping and shared library verification is a cornerstone in the detection of root/jailbreak/emulator/hook/tamper activities. At its core, this process involves inspecting the memory layout of a running process to identify deviations from expected behavior, as well as validating the authenticity of shared libraries that are critical for the execution of the application. These mechanisms serve as a dual-purpose tool: they enable the detection of runtime modifications and provide a means to assess the trustworthiness of the software environment in which the application is executing.

Memory mapping refers to the way in which a process's address space is organized, with segments such as text (executable code), data (initialized and uninitialized variables), stack (function call frames), and heap (dynamic memory allocations). In a non-rooted or non-tampered environment, these regions are typically mapped by the operating system using specific file descriptors and memory protection flags. However, when an attacker modifies the process's memory mapping—such as through hooking or memory tampering—the resulting layout may deviate from the expected structure. This deviation can be detected by comparing the actual memory mappings against a known baseline or expected pattern.

One of the key tools for inspecting memory mappings is the `/proc/<pid>/maps` file in Linux, which provides a detailed view of the process's virtual address space. Each entry in this file includes information such as the start and end addresses of the mapped region, the permissions assigned (read, write, execute), the offset within the file, the device identifier, the inode number, and the path to the mapped file. By analyzing these entries, an integrity checker can identify anomalies such as unexpected executable regions in the data segment, or mappings that do not correspond to known binaries or libraries.

For example, if a process is expected to have a specific shared library loaded at a certain address, but instead the mapping shows a different path or a file with a suspicious name, this could indicate tampering. Similarly, if a region marked as read-only is found to be writable, it may suggest that an attacker has modified the memory layout to inject malicious code. These anomalies can be flagged as potential indicators of root/jailbreak/emulator/hook/tamper activities.

In addition to inspecting the mappings themselves, shared library verification plays a crucial role in ensuring that the binaries being executed are authentic and have not been modified. Shared libraries, such as those found in the `/lib` or `/usr/lib` directories, are typically loaded by the dynamic linker (`ld.so`) during program execution. The integrity of these libraries can be verified through several mechanisms, including checksum validation, digital signatures, and runtime checks.

One widely used method for verifying shared libraries is the use of cryptographic hashes. By precomputing a hash of the expected library file and comparing it against the hash of the loaded library at runtime, an integrity checker can determine whether the library has been modified. For instance, if a process is expected to load `libssl.so` from a specific path, the system can compute the SHA-256 hash of the original file and compare it with the hash of the loaded library using `dlopen()` or similar functions. If the hashes do not match, this could indicate that the library has been tampered with.

Digital signatures offer another layer of verification by allowing the system to authenticate the source of the shared library. In environments where cryptographic signing is supported, such as Android's Verified Boot or Linux's Secure Boot, libraries can be signed with a trusted key. During runtime, the integrity checker can verify the signature of the loaded library against the expected public key. If the signature is invalid or cannot be verified, this may indicate that the library has been replaced with a malicious version.

Moreover, shared library verification can also involve checking for anomalies in the loading process. For example, if a library is loaded from an unexpected location, such as a user-defined directory rather than a standard system path, this could be a red flag. Similarly, if a library is loaded multiple times with different paths or versions, it may suggest that the loader has been modified to inject malicious code.

In addition to these static checks, runtime validation of shared libraries can also involve inspecting the dynamic linking information. This includes examining the `.dynamic` section of the library file, which contains metadata such as the version of the library, the required dependencies, and the entry points for symbols. By comparing this information against a known baseline or expected configuration, an integrity checker can detect inconsistencies that may indicate tampering.

Another important aspect of shared library verification is the detection of symbol hijacking or hooking. In some cases, attackers may replace symbols in a shared library with their own implementations to intercept function calls or modify behavior. This can be detected by inspecting the symbol table of the loaded library and comparing it against the expected set of symbols. For example, if a library is expected to export a specific symbol such as `SSL_read`, but instead the symbol points to a different function that has been injected, this could indicate hooking or tampering.

In summary, memory mapping and shared library verification are essential components of process and thread state inspection. By analyzing the memory layout of a process and validating the integrity of its shared libraries, an integrity checker can detect deviations from expected behavior and identify potential signs of root/jailbreak/emulator/hook/tamper activities. These techniques provide a robust foundation for runtime-integrity detection, enabling the system to maintain trust in its execution environment and detect subtle modifications that may otherwise go unnoticed.

The process of inspecting shared libraries extends beyond mere file verification to include runtime analysis of how these libraries are loaded and executed. One of the primary tools for this is the `dlopen()` function, which allows a program to dynamically load shared libraries at runtime. By examining the behavior of `dlopen()`, an integrity checker can detect anomalies such as unexpected library paths, missing dependencies, or incorrect loading flags.

For instance, if a shared library is expected to be loaded with the `RTLD_LAZY` flag (which defers symbol resolution until the library is first used), but instead it is loaded with the `RTLD_NOW` flag (which resolves all symbols immediately), this could indicate that the loader has been modified. Another important aspect of shared library verification is the inspection of the dynamic linking process itself. This involves examining the `.dynamic` section of the library file, which contains metadata such as the version of the library, the required dependencies, and the entry points for symbols. By comparing this information against a known baseline or expected configuration, an integrity checker can detect inconsistencies that may indicate tampering.

In addition to these static checks, runtime validation of shared libraries can also involve inspecting the dynamic linking information at runtime. For example, by using the `dl_iterate_phdr()` function, an integrity checker can iterate through all the loaded shared libraries and examine their memory mappings, entry points, and symbol tables. This allows for a more granular inspection of the library's behavior and can help detect anomalies such as unexpected symbol resolution or memory corruption.

Furthermore, the use of tools like `nm` (the symbol table listing utility) can provide valuable insights into the contents of a shared library. By comparing the output of `nm` against a known baseline or expected configuration, an integrity checker can detect missing symbols, unexpected exports, or modified function signatures that may indicate tampering.

In summary, shared library verification involves a combination of static and runtime checks to ensure that the libraries being executed are authentic and have not been modified. By inspecting the memory mappings, dynamic linking information, and symbol tables of loaded libraries, an integrity checker can detect deviations from expected behavior and identify potential signs of root/jailbreak/emulator/hook/tamper activities. These techniques provide a robust foundation for runtime-integrity detection, enabling the system to maintain trust in its execution environment and detect subtle modifications that may otherwise go unnoticed.

The verification of shared libraries also encompasses the inspection of their execution context and behavior during runtime. This includes analyzing how functions within the library are called, how they interact with other components of the process, and whether any unexpected side effects or behaviors are observed. For example, if a function in a shared library is expected to return a specific value but instead returns an unexpected result, this could indicate that the function has been modified or replaced with a malicious implementation.

One method for detecting such anomalies is the use of runtime tracing tools like `strace` or `ltrace`, which can monitor system calls and library calls respectively. Another important aspect of shared library verification is the inspection of the library's execution flow and control transfer points. In addition to these runtime checks, shared library verification can also involve inspecting the memory regions where the library is loaded. For instance, if a region marked as read-only is found to be writable, this may suggest that an attacker has modified the memory layout to inject malicious code.

By combining these techniques—static file verification, runtime analysis, and memory inspection—an integrity checker can effectively validate the authenticity of shared libraries and detect any signs of tampering. This multi-layered approach ensures that even subtle modifications to shared libraries are identified, providing a robust mechanism for runtime-integrity detection.

### Thread Local Storage (TLS) Integrity Checks

TLS is a memory area dedicated to each thread, storing thread-specific data such as per-thread variables, function pointers, and other context-specific information. The TLS structure in Android is primarily managed through the `__dl_tls_data` segment, which contains a header followed by entries for each thread-local variable. Each entry includes a pointer to the thread-specific data and metadata such as the TLS alignment and size. In iOS, TLS is handled via the `__thread` keyword and the `pthread` library, with specific memory allocations managed through the `__thread` mechanism. These structures are typically initialized during process startup and remain consistent unless modified by external factors.

To perform TLS integrity checks, we analyze the TLS layout for deviations from expected patterns. For example, in Android, the TLS header contains a `tls_offset` field that indicates the offset of the thread-local data within the TLS segment. If this offset is altered, it may indicate that the TLS area has been modified or expanded, which could be a sign of tampering. Similarly, in iOS, the TLS header includes fields such as `dtv` (Dynamic Thread Vector) and `tls_index`, which are used to manage thread-local variables. If these values are inconsistent with their expected values, it may suggest that the TLS has been altered.

One specific mechanism for TLS integrity checks involves comparing the TLS layout against a known baseline. This can be done by inspecting the TLS header and entries at runtime and comparing them to a precomputed or dynamically generated reference. For example, in Android, the `__dl_tls_data` segment can be accessed using the `dlopen` and `dlsym` functions to retrieve pointers to TLS entries.
